## Architecture note: tenant isolation is enforced by two different mechanisms, not one

Discovered while closing T16, worth stating explicitly since it's easy to assume "RLS" covers everything: this codebase has **two separate tenant-isolation layers** that never overlap.

1. **App-level (`WHERE tenant_org_id = ...`)** — used by every Prisma/raw-SQL service (`workflow-engine.service.ts`, `delivery-completion.service.ts`, `pickup-completion.service.ts`, the route-command service, etc.). `DATABASE_URL` connects as the Postgres `postgres` superuser (see `web-admin/.env.local`), and Postgres superusers **always** bypass row-level security — that's core Postgres behavior, not a gap. Isolation here is 100% the explicit `WHERE`/composite-FK discipline every DB-integration test this session already verified (`'does not reveal another tenant stop'`, etc.).
2. **RLS (`current_tenant_id()`, migration 0081)** — used by every API route going through `createServerSupabaseClient()`/`createClient()` (dozens of routes under `app/api/v1/orders/**` and elsewhere), which run as the Postgres `authenticated` role under PostgREST, respecting `auth.jwt() -> 'user_metadata' ->> 'tenant_org_id'`. This is the layer T16 now actually proves.

Neither layer is redundant with the other — they protect different code paths. A test proving one says nothing about the other.

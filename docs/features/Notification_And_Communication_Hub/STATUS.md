## 2026-10-10 — A1 pilot-cutover grounding: a real, material correction to this program's own "no live cutover exists" claim

- **Correction, found while grounding A1's implementation (not yet built — this entry is investigation only, no code changed):** every prior entry in this file and the plan doc describing "no tenant has been cut over to live HQ-routed sending" / "zero real traffic" is **imprecise**. A second, separate, already-built mechanism exists: `web-admin/lib/notifications/config.ts`'s `isNtfDispatchViaHq()` (runtime setting `ntf_dispatch_via_hq`, env override `NTF_DISPATCH_VIA_HQ`) is read by every channel adapter (`adapters/{whatsapp,sms,email,push}.ts`) and, when true for a tenant, forwards the send to HQ's real `POST /notifications/dispatch` endpoint (`platform-api/.../dispatch/dispatch.controller.ts`) instead of sending directly — which actually dispatches through HQ's already-built, already-tested transport (`dispatch.service.ts`, quota/metering migration `0598`, idempotency, `platform-workers`/BullMQ for queued channels). **This is a real, working, flippable-today live-send path with zero new code required** — turning it on for a tenant is a settings change, not a build.
- **The important caveat, and why this is not simply "A1 is already done":** `deliverViaHqProxy`'s request body (`{idempotencyKey, tenantOrgId, channel, recipient, payload: {body}, requestId}` — confirmed against `DispatchRequestDto` in HQ, which takes a fully generic `payload: Record<string, unknown>` with no field for a route/account/sender/revision/binding identity) **never calls `resolveEffectiveNotificationRoute` and has no way to carry a resolved route's pinned provider/template/binding identity at all.** It is a generic, template-blind forwarder — confirmed by its own code comment: "Twilio production content_templates require direct tenant dispatch...

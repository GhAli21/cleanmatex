**Scope:** item C3 from [section 23.1](./notification-hub-production-implementation-plan.md#231-remaining-work-and-sequencing-snapshot-2026-10-10) of the production implementation plan. Read-only audit — no test, code, or migration was written or changed by this pass.

**Method:** for every row of [section 20](./notification-hub-production-implementation-plan.md#20-test-and-acceptance-matrix), the actual test file(s) were opened and the real assertions read (not inferred from `describe()`/filename). Tenant scope: `web-admin/__tests__/notifications/**` (23 files). HQ scope: `platform-api/src/modules/notifications-hq/**/__tests__/**` (11 files, all service-level — **zero controller/guard-level `*.spec.ts` files exist on the HQ side**, confirmed by a repo-wide glob). Where a row's described behavior did not obviously map to an existing file, the underlying source module was read directly to confirm whether the capability even exists in code, before concluding "not covered."

## Cross-check against STATUS.md claims

STATUS.md's 2026-10-09/2026-10-10 entries describe test coverage added for outbox reconciliation, EMAIL/SMS dispatch-time consent, quota/usage atomic metering, and campaign processor fixes. All four claims held up against the actual test files:

- Reconciliation: `reconciliation-service.test.ts` (10 tests) genuinely covers the WhatsApp/Twilio-only scope the entry claims — no overstatement found.
- EMAIL/SMS dispatch consent: `email-sms-dispatch-consent.test.ts` + `customer-dispatch-consent.test.ts` match the entry's described opt-out-only, non-regressive scope exactly.
- Quota/metering atomicity: `metering.service.spec.ts`, `quota.repository.spec.ts`, `quota.service.spec.ts` match the entry's own careful wording (idempotency and lost-update-freedom closed; cross-command race explicitly still open) — this is the one row (28) where the plan's own inline annotation is already more precise than a fresh classification would add.
- Campaign processor: `campaign-target-sync.test.ts` + `template-renderer-by-code.test.ts` match the entry's claimed scope (status mapping, RPC no-op/error paths, channel-specific rendering) — no pause/cancel test exists, but the entry never claimed one.

**Nothing in STATUS.md's prose overstated what the test files actually prove.** The gap this audit surfaces is different in kind: STATUS.md accurately describes what was tested increment-by-increment, but no one had previously checked those increments against the full section-20 matrix, so large pre-existing holes (webhooks.service.spec.ts's single test; zero push/orchestrator/event-emitter/SMS-segment coverage; zero HQ controller/guard tests) were never visible until this row-by-row pass.

## Surprising findings

- **`webhooks.service.ts` — a ~300-line file with real Twilio form-parsing, Meta batched-JSON parsing, idempotent upsert, and provider-code-scoped status projection logic — has exactly one test.** STATUS.md's 2026-10-03 entry describes this logic's capabilities accurately, but no test file growth ever followed; this is the single highest-leverage gap found (rows 9/10/11 all collapse to this one file).
- **`orchestrator.ts` and `event-emitter.ts` — the two modules every single notification passes through — have no test file at all**, confirmed by grepping every test file's imports. Every tested behavior in the 23 tenant test files exercises an adapter, a helper, or a leaf service; nothing exercises the orchestration layer itself.
- **The push channel adapter (`push.ts`) has zero tests**, despite implementing non-trivial per-device retirement logic (`failure_count >= 3` auto-deactivation) that is exactly the kind of logic most likely to silently misbehave.
- **HQ has no controller or guard-level test at all** — all 11 HQ spec files are service-level with hand-built mocks; `JwtAuthGuard`/tenant-JWT/permission-gating behavior (row 30) is entirely unverified by Jest on the HQ side.
- Rows 19/20/24 turned out not to be test gaps at all on closer reading — the described capability (bounded item lists, invoice-total-aware variables, SMS segment estimation) **does not exist in the current notification variable/adapter code**, so there is nothing yet to write a meaningful unit test against.

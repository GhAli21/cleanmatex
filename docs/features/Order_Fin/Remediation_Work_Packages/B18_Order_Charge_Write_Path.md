## Confirmed problem
Submit always passes `chargeLines: []` — `org_order_charges_dtl`, snapshot charge buckets, and recon charge checks are fully built but never fed. **Re-verified 2026-07-25 against live code and the live remote DB: this is worse than "dormant."** `org_order_charges_dtl` has **zero rows across all 67 live orders**, while 17 items, 43 pieces, and 111 preferences already carry real non-zero `service_pref_charge`/`extra_price`. Two reconciliation checks already wired into the live reconciliation run (`ORDER_PIECES_MATCH_CHARGES`, `ORDER_PREFERENCES_MATCH_CHARGES`, both **BLOCKER** severity, from an earlier "BVM Phase 4" program predating this remediation effort) compare those real sums against the always-empty charges ledger — meaning reconciliation, if run today, fires BLOCKER failures for real orders. Closing this was reprioritized to the core of B18's delivery, not a side effect.

## Scope pivot (owner-directed, 2026-07-25)
The original doc scoped a fixed SERVICE/DELIVERY/EXPRESS/OTHER charge-type picker with its own UI. Mid-implementation, the owner explicitly redirected scope twice: first proposing a tenant-configurable extra-charge catalog, then — after research showed `charge_type` is a small fixed reporting category (not a tenant catalog) and that `org_order_preferences_dtl` already supports `prefs_level IN ('ORDER','ITEM','PIECE')` since migration 0166 — withdrew that proposal in favor of the existing PREFERENCE/extra_price mechanism, adding one concrete requirement: **UI to add preferences at the ORDER level and the ITEM level, not just PIECE level (today's new-order page only exposes piece-level entry for piece-tracking tenants)**. This became B18's actual delivered scope: order-level preferences ARE this package's "charges" concept; item-level preference UI already existed in code but was hidden behind a piece-tracking ternary — both fixed.

## Required outcome
Charges (delivery, express, service) flow: UI/request → calc engine (`chargesTotal` in saleTotal and tax base per mode) → **order creation writes `org_order_charges_dtl` directly** (delivered mechanism — not via `settleOrderTx` as originally worded here; see Design decisions #6) → snapshot buckets populate → recon charge checks pass; charge void deferred (see Out of scope).

## Scope
Engine params + formula placement (gross = subtotal + charges); order-level preference UI (new); item-level preference UI additive alongside piece-level (fix, was mutually exclusive); ORDER-level `org_order_preferences_dtl` write path (new); PREFERENCE-type `org_order_charges_dtl` write path for ALL preference levels (item + piece + order), one row per preference with `charge_source_id` lineage, closing the live reconciliation gap; `total_charges_amount` header write; request schema (preview + submit).

## Out of scope (deferred, documented — not silently dropped)
- **Backfill of the 67 existing orders'** missing PREFERENCE charge facts — owner explicitly chose "fix forward only, flag backfill separately" when presented the finding via `AskUserQuestion`. A backfill migration (derive `org_order_charges_dtl` rows from existing `org_order_preferences_dtl`/`total_charges_amount=0` orders) is a real, separate, financially-sensitive follow-up requiring its own migration + owner sign-off.
- **Charge void action** — `is_voided`/`voided_at`/`voided_by`/`void_reason` columns already exist and are schema-ready; no void UI/API built this pass.
- **Per-charge taxability** — no `is_taxable` column exists on any preference/charge table. Order-level charges are implemented as a flat, always non-taxable addend (see Design decisions) rather than inventing an unconfigured taxability flag.
- **Item-edit / recalculation path** (`order-service.ts`'s `updateOrder`) — **broader than initially scoped; corrected 2026-07-25 on self-review.** Not just order-level preferences: `updateOrder`'s "add new items" flow delegates piece creation to the SHARED `OrderPieceService.createPiecesForItemWithTx` (also used by the create path), which writes real `org_order_preferences_dtl` PIECE-level rows with non-zero `extra_price` — but the charge-fact writer built in this package lives only inside `createOrderInTransaction`, not in `updateOrder` or `OrderPieceService`. So **any item/piece/order preference added via an order edit (not just order-level) will not get a matching `org_order_charges_dtl` fact or `total_charges_amount` update.** This is not a regression — that path never wrote charge facts before B18 either — but it means the reconciliation-gap fix only fully covers orders at INITIAL creation, not preferences added to an order after the fact. Consistent with B11/B17's identical scoping decision on this same legacy edit path (slated for retirement via B12/B23); a real follow-up would either move the charge-writer into the shared `OrderPieceService` (benefits both callers) or add an equivalent block to `updateOrder`.
- Charge approval permissions (B27); amendment-driven charge changes (B12) — from the original doc, still out of scope.

## End-to-end operational flow

1. Operator clicks the **"Preferences" pill** in the sticky top bar (visible on every step) for order-level preferences, opening `OrderPreferencesDialog`. For item-level, the operator opens the new-order page's Preferences → Service tab, which shows each item's own kind toolbar (service prefs + packing). For piece-level, the operator uses the separate "Edit Items Preferences" wizard step, unchanged.
2. Operator adds a preference at any level (order/item/piece) with a non-zero `extra_price`. Preview totals update live — the amount appears in `chargesTotal` (order-level, and the top-bar pill's badge count updates) or folded into item pricing (item/piece-level, unchanged existing behavior).
3. Submit persists: ORDER-level rows to `org_order_preferences_dtl`, and — for every preference row across all three levels with `extra_price > 0` — a mirror `org_order_charges_dtl` fact row plus the `total_charges_amount` header field.
4. Reconciliation (`order-snapshot-checks.ts`), if run, is clean for this order: the charge facts fully account for every piece/item/order preference extra, with no duplicate `charge_source_id`.

UI states: reuses `ServicePreferenceSelector`'s existing loading/empty/disabled/compatibility-warning states — no new state contract needed since no new interactive component was built.

## Design decisions (this implementation)

1. **Order-level preferences ARE this package's "charges" concept.** Rather than building a parallel, separate "charge entry" UI (delivery/express/service picker) as the original doc scoped, order-level preferences (`prefs_level='ORDER'`) fill that exact role — an order-wide, non-item-specific extra with a monetary amount — reusing the tenant's already-configured `org_service_preference_cf` catalog instead of inventing a second config surface.
2. **Order-level charges are a flat, non-taxable addend — not proportionally extracted under TAX_INCLUSIVE, not added to the tax base.** No `is_taxable` column exists on any preference/charge table to drive a per-charge decision, and attempting proportional inclusive-extraction across a combined items+charges base (to keep the `afterDiscounts` net-of-tax figure items-only, matching `resolveCanonicalTotalAmount`'s separate `itemsBaseAmount`/`totalChargesAmount` components) would require inventing untested, unrequested complexity. Order-level charges are analogous to the already-established "ad-hoc `additionalTaxAmount`" pattern from B11: an operator-entered surcharge layered on top, not a catalog price. Documented here as a deliberate, revisitable scope decision — a future package can add `is_taxable` if a real tenant need surfaces.
3. **One `org_order_charges_dtl` row per preference row, not an aggregate.** The existing (already-tested) `order-snapshot-checks.ts` reconciliation module's `PREFERENCE_EXTRA_PRICE_INCLUDED_ONCE` check specifically inspects `charge_source_id` for duplicates across PREFERENCE-type charge rows — this only makes sense if the intended design was always one charge row per preference source. Verified algebraically and by test that this design satisfies all five checks in the module unconditionally: since the writer makes `Σ(PREFERENCE charge rows) == Σ(ALL org_order_preferences_dtl.extra_price)` by construction, and the check module's own `piecesSum`/`itemsSum` terms are strict subsets of that same preference-row population, no combination of real data can trip a false positive on any of the five checks.
4. **Read-back instead of pre-generated UUIDs.** Rather than retrofitting UUID pre-generation into the five existing, already-working item/piece preference-write blocks (risky churn to working code, for zero functional benefit), the charge-writer runs one extra `org_order_preferences_dtl.findMany({extra_price: {gt: 0}})` read after all preference rows (item/piece/**new order-level**) are written, then derives the charge rows from that. Negligible cost (one read per order), zero risk to existing writes.
5. **No feature flag.** Additive-only, UI-gated by construction (nothing changes unless an operator uses the new "Whole Order" section or now-visible item-level selector) — matches the same "safe by data/UI, not by flag" pattern established in B11 and B17.
6. **The charge-fact writer is a new, standalone code path inside `createOrderInTransaction` — it does NOT feed `settleOrderTx`'s pre-existing `chargeLines` parameter.** *(Corrected 2026-07-25 on self-review — an earlier draft of this doc mischaracterized this as "settle writes org_order_charges_dtl from orchestrator" and "the writer needed zero changes," implying the fix flowed through `settleOrderTx`. It does not.)* `settleOrderTx` is called later in the same submit flow purely for payment-fact settlement and is still fed `chargeLines: []`, unchanged. The two writers never touch the same rows in the same request (no duplication risk today), but a real, cleaner future refactor would either retire `settleOrderTx`'s dead `chargeLines` param or route both callers through one shared writer. Verified while re-checking this: neither `settleOrderTx` nor the orchestrator issues any `org_orders_mst.update()` at all, so nothing downstream can silently overwrite the `total_charges_amount` this package's writer sets during order creation — confirmed safe by direct code inspection, not assumption.
7. **UI redesign scope (2026-07-25, owner-directed): consolidate order/item level into the piece-level kind-toolbar pattern, but leave piece-level and order-level packing/conditions/color out.** Three deliberate boundaries, all revisitable: (a) order-level offers `service_prefs` only — no order-wide packing preference field exists in `NewOrderState`/backend today, and building one (new state, new reducer action, new backend column/write, new submission-payload field) is a real, separate lift not requested; a tenant can already achieve the same practical outcome by setting packing per item. (b) conditions (stain/damage) and color are excluded from BOTH order and item level cards — these are physical, per-garment facts that only make sense at piece granularity; item already has its own simpler `hasStain`/`hasDamage` boolean mechanism elsewhere, and offering a second, catalog-code-based condition picker at item level would create two conflicting ways to record the same fact. (c) *(superseded 2026-07-25, see #8 below — the original decision here was to leave piece-level rows inside this tab on the old `ServicePreferenceSelector`; those rows were later removed from this tab entirely, not merely left old-style.)*
8. **Order-level entry point relocated to the sticky top bar; piece-level rows removed from the Service Preferences tab entirely (2026-07-25, owner-directed, 3rd iteration — usability).** Owner's concern: laundry-counter staff are not heavy tech users and will forget to look inside a non-default sub-tab (Preferences → **Service**, when the tab defaults to **Quick Apply**) for something that applies to the whole order. Fix: reuse the app's own already-proven pattern for order-wide toggles — `NewOrderTopBar` is a `sticky top-0` bar rendered once, visible on every step, already carrying Customer and Express pills that staff use every order. A third **"Preferences" pill** (`new-order-top-bar.tsx`) was added next to them, with a count badge, opening `OrderPreferencesDialog.tsx` — a small self-contained dialog (owns its own `usePreferenceCatalog`/`useNewOrderStateWithDispatch` binding) that renders the *same* `LevelPreferenceCard` previously embedded in the tab, unchanged. Net effect: order-level preferences are now reachable and visible (via the badge) from any step, not just Step 2's non-default sub-tab. At the same time, the piece-level checkbox rows that had been left inside the Service Preferences tab (see #7c) were deleted outright rather than upgraded in place — the user's own framing was "that tab should be items only," since piece-level already has its full, richer kind-toolbar experience one step over, in "Edit Items Preferences" (`OrderPiecePreferencesSection`/`PiecePreferenceCard`); keeping a second, weaker (checkbox-only) piece entry point inside the Service Preferences tab was judged pure duplication with no usability upside, so it was cut rather than redesigned. `PreferencesTabsSection.tsx`'s dead `handlePieceUpdate` helper and its now-unused `updateItemPieces`/`updateOrderServicePrefs` destructures and `ServicePreferenceSelector`/`PreSubmissionPiece` imports were removed alongside it — no orphaned code left behind. If the owner later wants order-level packing, that remains the same small, well-scoped follow-up noted in #7a, now equally reachable from the dialog.
9. **Payment-modal + running-total consistency for order-level charges (2026-07-25, owner-reported defect — "not show in payment model", plus a live `AMOUNT_MISMATCH` on submit).** The original B18 implementation wired order-level charges into the **submit** server calc (`order-submit-orchestrator.service.ts` maps `orderServicePrefs → orderCharges`) and into the preview **routes** (`preview-payment`/`preview-financials` both consume `orderServicePrefs`), but the **client preview fetch never sent them.** The payment modal's totals come from `usePaymentTotals.fetchPreview` → `POST /api/v1/orders/preview-payment`, whose body omitted `orderServicePrefs` entirely — so the route received an empty charge set, the modal's `serverTotals.saleTotal` excluded the 0.5, and the receipt displayed the pre-charge total. Worse, that same modal `saleTotal` becomes `clientTotals.saleTotal` in the submit payload, while the orchestrator's own server calc (which *does* receive `orderServicePrefs`) computed the correct, higher total — so `buildDifferences` flagged a genuine `AMOUNT_MISMATCH` (client 10.272 vs server 10.772 = exactly the 0.5 charge) and blocked submission. Fix: thread `orderServicePrefs` through the whole modal chain — `new-order-modals.tsx` (from `state.orderServicePrefs`) → `PaymentModalV4` → `PaymentFullView` → `usePaymentEngine` → `usePaymentTotals`, which now includes it in the preview body and its fetch deps. Once the preview receives the prefs, the modal total, the displayed receipt, and the submitted `clientTotals.saleTotal` all equal the orchestrator's server total — the mismatch is structurally impossible again (both sides feed the identical charge set into the identical `calculateOrderTotals`). For the pre-preview fallback window and the workspace running total, the order-level charge sum was also added to the payment modal's `checkoutAmount` (`new-order-modals.tsx`) and to the summary rail + bottom-sheet `total` display (`new-order-content.tsx` `summaryTotal`), so the cashier sees a single consistent grand total everywhere. Deliberately NOT added to the modal's `total`/subtotal prop or the Step-2 "Order Items" component breakdown: order-level charges are a separate non-item addend (they must not inflate the `subtotal` field the mismatch check compares, and the Step-2 box is explicitly an items-only subtotal). No backend/engine/write-path change — this iteration is purely the missing client→preview wiring plus display consistency.
10. **Order charges surfaced as an explicit, itemized receipt line, always visible — not gated on a discount existing (2026-07-25, owner follow-up: "also show it in simple view", then "fix that issue permanently — that must have discount to show the other info").** Decision #9 made the total *correct*, but the charge was still folded silently into the grand total with no line item explaining it. `ServerTotals`/`totals` in `use-payment-totals.ts` now carry `chargesTotal` (from the preview response's existing `chargesTotal` field — the calc engine already returned it, it just wasn't read); `orderValueBreakdownModel` in `payment-full-view.tsx` adds a `t('summary.orderCharges')` row to `grossRows` whenever `chargesTotal > moneyEpsilon`, right under Subtotal. The **Full/Advanced** view's Financial Inspector tab already always rendered `OrderValueBreakdownPanel` unconditionally, so the new row appeared there for free. The **Simple** view's receipt did NOT — it only rendered the panel when `discountRows.length > 0`, so on a plain order (no discount, no order charge) the cashier never saw the subtotal/tax story at all, only a single opaque "Order Total" line. First pass narrowed this gate to also fire on a charge (`discountRows.length > 0 || grossRows.length > 1`); the owner correctly rejected that as still conditional — **the gate was removed entirely.** `payment-simple-view.tsx` now always renders `OrderValueBreakdownPanel` (Subtotal → order charges if any → discounts if any → tax if any), matching the Full/Advanced view's own unconditional behavior; the Order Total `SummaryRow` below it is now unconditionally `bold`. `grossRows` always has at least the Subtotal row (pushed unconditionally in the model), so the panel never renders empty. Fallback/loading window keeps `chargesTotal: 0` (never assume before the server confirms — same B15/B17 "client never invents" pattern). New i18n: `newOrder.payment.summary.orderCharges` — initially EN "Order preferences" / AR "تفضيلات الطلب", **relabeled the same session (owner: "where is extra charge???" — the "Order preferences" wording didn't read as the money-facing concept the owner had been calling "extra charge" throughout this whole thread) to EN "Extra Charges" / AR "رسوم إضافية"**, values-only change, same key, `check:i18n` re-confirmed clean. No backend change — this is a read-and-display fix on top of decision #9's already-correct total.

## Confirmed problem
Item add/remove flows through a legacy direct-header-update path (UNSAFE_DIRECT_UPDATE, 0.05 VAT fallback, inclusive assumption) with no amendment record, no delta, no settlement consequence — paid orders silently grow outstanding; decreases create undisposed overpayment (§29).

## Required outcome
`OrderAmendmentService` implementing the D011 frozen model: before/after snapshots, canonical repricing, immutable amendment record, delta settlement consequence (collect-additional or overpayment resolution), approval gates, per-mutation idempotency; legacy recalc path retired for governed mutations.

## Scope
**Governs `OrderService.updateOrder` only (the New Order page's "Edit Order" flow) — the item add/remove/qty/price-override path that already reprices via the canonical engine and already writes a before/after audit row.** Amendment record: extend the existing `org_order_edit_history` table (2 new nullable columns) rather than a new table. Delta settlement hooks into the EXISTING `OrderCollectPaymentModal` (positive delta) and `executeOverpaymentDispositionTx` (negative delta) — see Design decisions. Governed only when the caller's item list actually changes the total on an order that already has `total_paid_amount > 0`; a $0-paid order or a non-financial edit (notes, ready-by, customer) is unaffected either way. Behind `order_fin_governed_amendments` (default OFF).
**Frontend surface (rule 7):** delta review step in the existing Edit Order save flow (before/after totals) → on confirm, positive delta opens the existing `OrderCollectPaymentModal` pre-seeded with the new outstanding amount; negative delta routes through the existing overpayment-disposition mechanism; amendment history reuses/extends the existing order edit-history display.

## Out of scope
**The `preparation/[id]/items/[itemId]` PATCH/DELETE routes and the `addOrderItems` bulk-add route — a separate, more primitive item-mutation surface used by the Preparation workflow page.** These do not use the canonical engine at all today (PATCH/DELETE have zero recalculation; addOrderItems has a transient-wrong-then-self-corrected write) and have no before/after snapshot infrastructure to build on — governing them is a materially different, additional lift (they'd need the canonical-engine wiring `updateOrder` already has before a delta/settlement layer makes sense on top). Flagged here as a real, live gap, not silently dropped — worth its own follow-up once this package's pattern is proven. Tax-document adjustments (B14 provides the surface); full mutation catalogue beyond the §29 top set (phased); revenue impact (B25); monetary approval thresholds (D011 explicitly defers these to B27 as configuration — this package's gate is the single `orders:post_settlement_edit` permission, not a threshold-approval workflow).

## Design decisions (this implementation)

1. **Reuse `org_order_edit_history` instead of a new table.** It already captures before/after snapshots, an immutable `edit_number` sequence, actor, and timestamp — exactly D011's core requirement. Migration 0437 adds two nullable columns: `edit_reason TEXT` (D011: "preserve the reason" — was entirely absent) and `settlement_lineage JSONB` (points at the real payment/disposition rows a governed edit produced — `{ paymentId?: string; dispositionIds?: string[] }`). The pre-existing `payment_adjusted`/`payment_adjustment_amount`/`payment_adjustment_type` columns are populated for the first time (previously always `false`/`null`/`null`).
2. **Reuse `OrderCollectPaymentModal`/`executeOverpaymentDispositionTx` for settlement — SUPERSEDED, see #13.** Original plan (below, kept for the record): both already exist, are already idempotent (D010-compliant), already permission-gated, and already exercise the exact settlement machinery (real payment legs / stored-value disposition) every other collection or refund in the app uses; `OrderAmendmentService` would only compute the delta and hand the resulting `outstandingAmount`/`resolution` to these existing mechanisms. **This was found to be unsafe for the general case during frontend wiring — see Design decision #13.**
3. **No new idempotency schema.** Reuses `lib/utils/idempotency.ts` (`stakeIdempotencyHash`/`findIdempotencyHash`) against the generic `org_idempotency_keys` table with `resource_type = 'order_amendment'`, `resource_id = orderId` — the exact D010 Option A pattern, already proven on submit-order/collect-payment.
4. **No new permission code.** `orders:post_settlement_edit` was already seeded by B27 (migration 0411) with exactly the right role grants (`super_admin`/`tenant_admin`/`finance_manager`/`admin`) and exactly the right description ("Edit an order's financial facts after it has already been settled/paid") — it was a reserved placeholder for this package. `OrderService.updateOrder` gains this permission check specifically when the edit is financially governed (item change on an order with `total_paid_amount > 0`); notes-only/customer-only edits keep the existing `orders:update` gate, unchanged.
5. **`outstanding_amount` bug fixed at the source, not just papered over by the existing redundant recalc.** Line 3140's `updateData.outstanding_amount = total` (ignoring `total_paid_amount`) is removed — `recalculateOrderFinancialSnapshotTx` (already called immediately after) is the single writer of `outstanding_amount`, matching every other financially-governed path in the codebase (one canonical recompute, not a naive write plus a corrective one).
6. **Governed only when it matters.** The flag-gated delta/settlement flow only activates when (a) the edit changes items (repricing actually happens) AND (b) `total_paid_amount > 0` on the order (a fully-unpaid order's total simply changes, nothing to collect or resolve — `outstanding_amount` tracks it exactly as before, still correctly). This matches the "Confirmed problem"'s actual concern (paid orders growing outstanding silently) without adding governance ceremony to routine unpaid-order edits.
7. **Tolerance-zero no-op.** A delta within `SETTLEMENT_MONEY_EPSILON` (existing constant, already used by the overpayment/collect paths) skips the settlement step entirely — a rounding-only edit doesn't force a cashier interaction.
8. **Negative delta beyond what's collectible is clamped, never negative-negative.** If the decrease exceeds `total_paid_amount` (e.g. removing items from an order that was only partially paid), the resolvable amount is capped at `total_paid_amount` — there's nothing to "refund" beyond what was actually collected; the remaining decrease simply lowers `outstanding_amount` further (already-correct behavior of the canonical formula, no special-casing needed).
9. **`preparation/[id]/items/*` routes deliberately NOT touched this pass** — see Out of scope. Flagging rather than fixing avoids conflating two differently-shaped problems (one has canonical-engine + snapshot infrastructure to build on; the other has neither) in one migration/service.
10. **Two-phase commit, not one monolithic transaction spanning the whole cashier interaction.** Collecting additional payment or resolving an overpayment is itself a multi-step, cashier-driven UI flow (choosing method, tendering, confirming) — it cannot realistically happen *inside* the same DB transaction as the repricing. Phase 1 (`OrderService.updateOrder`, inside its existing transaction): reprice via the canonical engine, write the `org_order_edit_history` row with `payment_adjusted: false` (delta known, not yet settled), return `financialDelta`/`editHistoryId`/`requiresSettlement: true` to the caller. Phase 2 (new route `POST /orders/[id]/edit-history/[editHistoryId]/settlement`, called after the cashier completes the real collection/resolution): `recordAmendmentSettlement` flips `payment_adjusted: true` and writes `settlement_lineage`. The row is immutable once settled (`recordAmendmentSettlement` no-ops on a second call) — matches D010's replay-safety requirement without inventing distributed-transaction machinery.
11. **A pre-existing, never-used `paymentAdjustmentSchema`/`PaymentAdjustmentInput` already existed in `edit-order-schemas.ts`** (`originalTotal`/`newTotal`/`differenceAmount`, comment "Positive = charge, negative = refund") — grepped and confirmed it was imported nowhere. This independently confirms the "Phase 5: will implement payment adjustment" comment found in `updateOrder`: the delta-settlement feature was designed once before and never wired. This package's `computeAmendmentDelta`/`AmendmentDeltaResult` follows the same signed-delta shape rather than introducing a third vocabulary; the old dead schema is left in place, untouched (not deleted — out of scope to clean up unrelated dead code in a financial-behavior package).
12. **Frontend — delivered in a follow-up same-session pass, after the backend-only pass above shipped first (owner: "continue... world-class best expert... production-ready, no gaps").** The New Order page's Edit Order save (`saveOrderUpdate` → `PATCH .../update`) always sends a fresh `idempotencyKey`; when the server rejects with `EDIT_REASON_REQUIRED`, a new `AmendmentReasonDialog` (reason textarea, min 5 chars, mirrors the existing `CancelOrderDialog` pattern) opens and the same save retries with the reason attached — no generic error toast for this case. On a successful governed save (`requiresSettlement: true`), a new `AmendmentDeltaNotice` dialog shows the delta and previous/new totals **before** navigating back (the non-governed path still navigates back immediately, unchanged).
13. **Settlement automation (collect-additional dialog / overpayment-resolution wiring) deliberately NOT built — a real, verified blocker, not a time-box call.** While wiring `OrderCollectPaymentModal` for the positive-delta case, found that `collectPaymentTx` (the function behind that modal's `POST .../payments` call) filters its target-order query with `AND payment_type_code = 'PAY_ON_COLLECTION' AND outstanding_amount > 0` (`order-settlement.service.ts:727`) — it is **not** a generic "collect additional payment on any order" mechanism, it is specifically the pay-on-collection pickup-time collection flow. Reusing it for a governed amendment on an order that was paid via a different method (immediate cash/card at intake — the more common real-world case for "add an item to an already-paid order") would throw `"Order not found or not awaiting later collection"` even though the order genuinely has an outstanding delta. Fixing this properly means either loosening `collectPaymentTx`'s invariant (a shared, heavily-tested, financially-critical function with other callers — not a change to make casually inside a UI-wiring pass) or building a distinct, non-PAY_ON_COLLECTION-scoped collection mechanism (real, separate work). Rather than ship a dialog that silently fails for the common case, shipped an **honest, always-correct notice instead**: `AmendmentDeltaNotice` tells the operator the exact amount and points them at the order's existing Payments tab to collect/refund manually, and the edit (reason, delta, `editHistoryId`) is unconditionally recorded either way via `org_order_edit_history` — nothing is silent or lost, `recordAmendmentSettlement`/the settlement API route are still available for whoever completes that manual step to close the loop via direct API (or a future UI once the underlying collection-mechanism gap is addressed as its own scoped follow-up, ideally coordinated with B23's legacy-path retirement).

## End-to-end operational flow

1. Operator edits items on an order via the New Order page's Edit Order flow. `OrderService.updateOrder` reprices via the canonical engine (unchanged) and computes `delta = newTotal - previousTotal`.
2. If the order has no prior payments, or `|delta| ≤ SETTLEMENT_MONEY_EPSILON`, or the flag is off: commit proceeds exactly as before (now with the `outstanding_amount` fix applied unconditionally).
3. Otherwise (flag on, financial delta, prior payments exist): the save is rejected once with `errorCode: 'EDIT_REASON_REQUIRED'`; the `AmendmentReasonDialog` collects a reason (min 5 chars) and the same save retries with `editReason` + the same idempotency key attached. The server-side transaction reprices, writes the `org_order_edit_history` row (`payment_adjusted: false` — delta known, not yet settled), and returns `financialDelta`/`editHistoryId`/`requiresSettlement: true`.
4. On that success response, the `AmendmentDeltaNotice` shows the previous/new totals and the delta amount, then directs the operator to the order's existing Payments tab to collect the additional amount or process the refund/credit manually (positive delta: any existing collection method; negative delta: existing refund/credit/wallet resolution UI, capped at `total_paid_amount`, per D003/D006). Automated dialog-opening for this step was evaluated and deliberately not built — see Design decision #13.
5. Whenever the manual settlement is completed, `POST /orders/[id]/edit-history/[editHistoryId]/settlement` (`recordAmendmentSettlement`) flips `payment_adjusted: true` and writes `settlement_lineage`, closing the loop; `recalculateOrderFinancialSnapshotTx` remains the single source of truth for `outstanding_amount` and all other derived totals regardless of when settlement is recorded.
6. Retry with the same idempotency key replays the cached result (no duplicate edit-history row); a different payload on the same key returns a 409-class conflict, matching the D010 contract every other financial write path already follows.

UI states: standard Cmx state contract — loading, empty, validation errors (missing reason via `AmendmentReasonDialog`'s min-length gate), permission-denied (action disabled with reason when `orders:post_settlement_edit` is absent), duplicate-click protection (in-flight disable + idempotent replay), processing, success (`AmendmentDeltaNotice`), retry on failure; edit-history display shows the settlement outcome (or "not required" for non-financial/unpaid-order edits) per row. `AmendmentReasonDialog`/`AmendmentDeltaNotice` both use `CmxDialog`, i18n EN/AR (`orders.edit.amendment.*`), and RTL-safe layout per the existing Cmx dialog pattern.

## Follow-up package raised from Design decision #13 (2026-08-14)

Design decision #13 deferred automated settlement because `collectPaymentTx` is `PAY_ON_COLLECTION`-only, and shipped `AmendmentDeltaNotice` as an informational dialog directing the operator to the order's Payments tab instead. **Subsequent verification showed that fallback is not actionable for the orders this package most affects**: the Payments-tab Collect button is gated `isPoc && payOnCollectionAmount > 0.001`, so a `PAY_IN_ADVANCE` order carrying a real post-amendment `outstanding_amount` renders no button at all. The amendment is recorded correctly; the money simply cannot be collected from any screen.

Scoped as **[B36 — Outstanding Balance Collection](B36_Outstanding_Balance_Collection.md)** (PROPOSED, design only, decisions not yet approved). B36 does not change anything in B12 — it supplies the missing settlement capability that B12's `editHistoryId` + existing settlement-recording endpoint were already built to receive.

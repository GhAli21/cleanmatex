## Design decisions (this implementation)

1. **Tenant/branch tax-registration number is the issuance prerequisite gate, not a new feature-flag catalog entry.** Migration `0440_b14_tax_registration_and_correction_triggers.sql` adds `org_tenants_mst.tax_registration_no`/`org_branches_mst.tax_registration_no` (branch override falls back to tenant, mirroring `tax_pricing_mode`'s existing pattern from B11/migration 0339). No document is ever issued for a tenant/branch with no registration number — combined with `org_tax_doc_triggers_cfg` having zero enabled rows for every tenant today, issuance is doubly dormant until an owner deliberately configures a pilot tenant.
2. **Read the registration number via raw SQL, not a typed Prisma field — a deliberate deploy-ordering safeguard.** `org_tenants_mst`/`org_branches_mst` are two of the most widely-queried tables in the entire app; regenerating the Prisma client with a new field before migration 0440 is actually applied would force Prisma's default (no-`select`) queries on either table to request a column that doesn't exist yet, breaking far more than tax documents platform-wide. `resolveTaxRegistrationNo` (`tax-document-issuance.service.ts`) uses `tx.$queryRaw` instead — safe regardless of which side of the migration-apply boundary the code currently sits on, exactly the pattern already used for `state_version` before its own Prisma mirror existed.
3. **The primary issuance trigger (`maybeIssueTaxDocumentTx`, wired at `ON_ORDER_SUBMIT` in `order-submit-orchestrator.service.ts`) is non-blocking by design** — wrapped in try/catch, logs and continues on any failure, exactly mirroring the existing `safeDispatchAutoPost` posture for ERP-Lite postings elsewhere in the same function (D007 failure-coupling). A new fiscal side-effect must never be able to take down order submission itself — the single highest-traffic write path in the app. Correction-document hooks (refund, amendment) are NOT wrapped this way (see #6) since they're structurally incapable of touching the new column before an original document exists.
4. **Correction documents are issued via a plain `createAndIssueTaxDocument`-shaped call, never via `supersedeTaxDocument()`.** The DB immutability trigger's own error message says it plainly: *"Issue a CREDIT_NOTE or DEBIT_NOTE to correct an issued document"* — the original stays ISSUED; only `supersedes_id` links the new document back to it for audit. `supersedeTaxDocument()` (flips the original to SUPERSEDED) is reserved for the separate "this document was wrong, void and replace it" lifecycle action — deliberately not invoked from the refund/amendment hooks, which correct a *legitimate* post-issuance change, not an issuance error.
5. **A correction document's `tax_amount` is a proportional approximation, not a per-tax-type recomputation — documented as a known simplification.** Neither B34's refund amount nor B12's `AmendmentDeltaResult` carries a tax breakdown of the delta; deriving one exactly would require re-running the tax engine against a before/after item diff, a materially larger piece of work than trigger-wiring. `issueCorrectionTaxDocumentTx` instead applies the original invoice's own tax:total ratio to the absolute delta (`correctionTaxAmount = |delta| × (originalTax / originalTotal)`) — correct for the common single-rate-VAT case, an honest approximation for mixed-category orders. Flagged here rather than silently assumed exact; exact per-line correction is a legitimate follow-up once this pattern is proven live.
6. **Correction-document hooks (refund, amendment) propagate errors instead of swallowing them.** Unlike the primary submit-time trigger (#3), `issueCorrectionTaxDocumentTx` runs inside the SAME transaction as the refund/settlement it corrects (`order-refund.service.ts`'s `processRefund`, `order-amendment.service.ts`'s `recordAmendmentSettlement` — the latter newly wrapped in its own `prisma.$transaction` for this reason). A real failure here rolls back the whole refund/settlement rather than silently completing money movement with a missing required fiscal correction. This is safe from the same deploy-ordering risk as #2 because the function's very first real DB touch is `org_tax_documents_mst.findFirst` (existing table, migration 0341, already applied) — it only reaches any *new* schema if an original document already exists, which itself requires migration 0440 + a configured pilot tenant to ever be true.
7. **Frontend deferred to a follow-up pass — flagged as a step-up via `AskUserQuestion` before starting, owner chose backend-first.** The read side (document view/timeline panel) already exists and needs no changes to start showing real data. Genuinely new UI (print/view screen, fiscal QR TLV payload, issue/cancel/replace actions, credit/debit-note dialogs wired into the B34/B12 UI flows) is real, separate work — the AR invoice print pattern (`ar-invoice-print-rprt.tsx` + route + API) is the identified template to replicate. Not a "no UI possible" gap — a scoped, deliberate sequencing choice on an unusually large package.
8. **Two new `trigger_event` enum values (`ON_REFUND`, `ON_AMENDMENT`) added to `org_tax_documents_mst`'s CHECK constraint only — not to `org_tax_doc_triggers_cfg`'s.** The former is a per-document audit label (how/why this specific row was created); the latter gates which *primary* invoice-issuance events a tenant opts into. A correction is an unconditional consequence of a delta on an order with an existing document, not a separately configurable business trigger — adding it to the triggers-config CHECK would incorrectly imply a tenant could opt out of a compliance-required correction.
9. **FN-03 needed a read-side fix, not new wiring.** The mismatch check itself (`evaluateTaxDocumentTotalMismatch`, `TAX_DOCUMENT_TOTAL_MISMATCH` warning code) already shipped and ran on every snapshot recalculation (Order_Fin_Remediation_2026-07 Phase 6) — it was simply always fed `null` because its only input (`org_orders_mst.tax_document_id`) is deprecated and unwritten. `order-financial-write.service.ts` now resolves the linked document via a direct `org_tax_documents_mst` join (`tenant_org_id` + `order_id` + `status='ISSUED'`, most-recently-issued) instead — the moment any document is issued for an order, FN-03 activates for it automatically, with zero changes to the check's own logic.

## End-to-end operational flow

1. **Primary issuance** (live, dormant by data): an order is submitted (`submitOrder`). Inside the same transaction, after settlement, `maybeIssueTaxDocumentTx` resolves the tenant/branch registration number (raw SQL — safe pre/post migration-apply) → no-ops if absent. Otherwise checks `org_tax_doc_triggers_cfg` for an enabled `ON_ORDER_SUBMIT` row → no-ops if none (true for every tenant today). If both gates pass, `decideTaxDocumentIssuance` checks order-status eligibility and `hasTaxLines`; on success, a DRAFT document is created and immediately issued (sequence allocated, `document_no` formatted, immutable from that point). Any failure here is caught and logged — order submission itself is never blocked (Design decision #3).
2. **Snapshot/FN-03**: every subsequent `recalculateOrderFinancialSnapshotTx` run (any order mutation) now joins `org_tax_documents_mst` by `order_id` for the currently-ISSUED document, stamps its id/no/status/type into the calculation-snapshot lineage, and feeds its `total_amount` into the already-shipped `evaluateTaxDocumentTotalMismatch` — `TAX_DOCUMENT_TOTAL_MISMATCH` now fires for real the moment a document exists and its total drifts from the order's.
3. **Correction on refund** (`processRefund`): after the refund's own snapshot recalc, `issueCorrectionTaxDocumentTx` looks for an ISSUED INVOICE/SIMPLIFIED_INVOICE on the order — no-op if none. If found, issues a companion CREDIT_NOTE (refunds are always a decrease) referencing the original via `supersedes_id`, with a proportional tax split (Design decision #5). Propagates errors — a real failure rolls back the refund (Design decision #6).
4. **Correction on amendment** (`recordAmendmentSettlement`, B12): now runs inside its own transaction; after recording the settlement outcome, the same `issueCorrectionTaxDocumentTx` issues a DEBIT_NOTE (charge) or CREDIT_NOTE (refund) per the signed `paymentAdjustmentAmount`/`paymentAdjustmentType`, same no-op-if-no-original / propagate-on-error behavior.
5. **Reconciliation**: sequence gaps, post-issuance mutation (immutability trip-wire), and document-vs-order-total drift are now checked on every reconciliation run alongside every other PRD §22.1 check.

UI states: N/A this pass — no new UI (see Scope/Design decision #7). Existing read-side document panel's states (loading/empty/error) are unchanged and unaffected.
